# Design: add-tutor-assistant

> 第 5 课（提示词、AI 技能与流式会话）的实现决策记录。
> 特性：**功能已实现，本 change 补规约**。故本 design 记录的是**已落地的决策及其理由**，
> 而不是"接下来打算怎么做"。凡与实现不符的描述，以实现为准。
>
> **新建 capability `tutor-assistant`**（第 5 课：提示词、AI 技能与流式会话）。
> 主规约 `openspec/specs/` 下**没有**同名 baseline，故本 change 的 delta 全部为 **ADDED**。
>
> **课程原文依据**：第 5 课课件 12 页（`preview` / `scope` / `session` / `skill-model` / `route` /
> `stream` / `answer` / `apply` / `think`）+ `课程任务清单-第5课.html`
> （三板块：功能 / Swagger / apitest）+ 官方契约 `/week05/openapi.json`（MCP 无关部分）。
>
> **delta 描述的是已实现、需被判定的行为**。凡与实现不符处以实现为准修正，
> 不反向修改实现去迁就一处写错的描述。

## 背景：为什么是"补规约"而不是"实现功能"

第 3、4 课都有对应的 openspec change 并归档进 `openspec/specs/`。
第 5 课的功能（提示词 / 技能 / 智能体 / 会话 / SSE）**代码全在**，
`scripts/e2e-tutor.mjs`（16 项）与 `apitest/`（12 用例）也都在，
但 `openspec/changes/` 下**没有**它的 change，`openspec/specs/` 下**没有**它的 capability。

后果不是"文档不好看"，是**无法验收**：
课程要求「仅凭一条 Scenario 能否判定通过/不通过」，
而第 5 课的功能目前只能靠读代码判断——不满足。
且 `knowledge-retrieval` 的 R6.7 明写「本课不实现流式输出」，
若把第 5 课塞进那个 capability，等于要推翻一条已归档的 Scenario。

**决策**：另立 capability `tutor-assistant`，本 change 全为 ADDED。

## D1 · capability 划分

| 备选 | 决议 |
|---|---|
| 并入 `knowledge-retrieval` | 否决：检索是「能力」，助手是「编排」。流式事件、技能路由、会话生命周期都不是检索的语义；且要推翻 R6.7 |
| 并入 `auth-upload` | 否决：认证与助手无共享语义 |
| **新建 `tutor-assistant`** | **采纳**：与「一个 capability = 一组可独立验收的能力」对齐 |

## D2 · 班级来源

沿用既有 D2 红线：**`class_id` 只取自服务端会话**。
提示词、技能、智能体、会话四张表都带 `class_id` 列，
写入时一律取会话班级，**请求体里的 `class_id` 读入后丢弃**。

**为什么不用 `GET /api/prompt` 按用户查**：提示词是**班级级**的（一个班一套角色设定），
不是用户级。所以 `class_prompts` 表主键是 `class_id` 而不是 `user_id`。

## D3 · 跨班一律 404

沿用既有 D3 红线：**跨班访问与「资源不存在」返回完全同形的 404**。

具体落到四处：
- 智能体：新建会话时引用他班/停用的智能体 → 404（与「编号不存在」同形）。
- 会话：按编号读取他班会话 → 404。
- 技能：对他班技能做改/删 → 404。
- 提示词：他是按班级隔离的，跨班改写按"资源不存在"处理。

**判定顺序有讲究**（`conversation.go` 新建会话处）：
先查本班有没有已启用的智能体（→ 400「本班没有已启用的智能体」），
再查目标智能体是否属于本班且启用（→ 404）。
反过来的话，"本班没智能体"这个信息会通过状态码泄露出去。

## D4 · 绑定是关系，不是快照

`agent_skills` 与 `agent_materials` 是**两张关联表**，不是智能体行里的 JSON 列。

**理由（课件 skill-model 页原文语义）**：会话锁定的是「用哪个智能体」，
而它当前绑了哪些技能与材料**每次提问重读**。
教师停用技能或解绑材料后，**立即生效，不必新建会话**。
做成快照（改绑定要重建所有会话的状态）就做不到这条。

**关联表用复合主键**天然去重；外键 `ON DELETE CASCADE` 让删智能体自动清关联。

## D5 · 技能文件用中文五键，且工具名固定

技能文件格式：

```
名称：方程解题引导
适用条件：方程,移项
工具：knowledge_search
资料：数学
启用：是

先让学生说出等号两边要保持相等。
```

**为什么是「键：值」逐行而不是 YAML/JSON**：这是官方契约 example 的形态，
教师直接用记事本就能写，且**空行**天然承担「头部 vs 正文」的分隔。

**`工具` 只接受 `knowledge_search`**（第 5 课范围内唯一可用工具）。
第 6 课会扩展成 `工具名@服务器名` 的 MCP 引用格式——那是下一轮的事。

**长度上限**：名称 ≤32、适用条件 ≤120、说明 ≤2000、整份 ≤8000。
（`source` 存原文，其余列由服务端解析 `source` 得到。）

## D6 · 技能路由：词法计分，至多一个

规则（课件 route 页）：
1. 候选集 = 智能体**绑定** ∧ **已启用** 的技能；
2. 适用条件按 `,，、;；|` 切词；
3. 逐词判断是否为提问的**子串**，命中一个得一分（两侧统一转小写）；
4. 取最高分；**同分取编号较小者**；零分不选。

**为什么是子串匹配而不是分词/向量**：确定性、可解释、无额外依赖。
一个技能命中与否，看一眼就能判断——这在验收时很重要。

**同分取小编号**用「严格大于」实现（候选按 `id` 升序遍历，先出现者保留）。

## D7 · 检索范围：绑定材料 ∩ 资料范围

助手链路里检索**不是**独立的 `/api/search`：
- 范围收窄到**该智能体绑定的材料**（`agent_materials`）；
- 再按技能的「资料」字段过滤（非空时只保留标题含该词的材料）；
- 取**前 4 条**（`askTopK = 4`）。

**注意这与第 4 课 `/api/ask` 的口径不同**：
第 4 课的 `/api/ask` 在本班全部材料里检索；第 5 课的会话链路**只在绑定材料内**。
这是「把检索接进助手行动链」的具体含义——范围由智能体的配置决定。

## D8 · meta 恒为 ok，检索落空仍作答

**会话链路的 `meta.status` 恒为 `ok`**，即使检索落空。
落空时：`citations` 为空数组、正文**不含 `[n]` 编号**、但**仍然是一次正常作答**
（不是整段固定文案）。

**理由**：`no_evidence` 是第 4 课 `/api/ask` 的口径（那是一个独立检索页，问答分离）。
第 5 课把检索变成行动链的一步——检索不到只是"这次没找到依据"，
助手仍应基于自己的知识组织回答。把它做成固定文案会让助手在无依据时一句话都不说。

**同时要防止另一件事**：模型可能凭空写出 `[1]` 这样的编号。
所以落空时**从流式输出里剥掉 `[n]`**（`numStripper` 处理跨 delta 被切开的编号）。

## D9 · 资料不进系统消息

系统消息只放：**角色提示词** + **技能说明** + 边界句。
检索到的资料正文进**用户消息**一侧。

**理由**：材料是教师上传的外部输入。
放进系统消息 = 给不可信文字发指令的权限——提示词注入直接生效。
这与第 6 课「工具返回也是攻击面」是同一条纪律的两种形态。

## D10 · SSE 三类事件 + 失败补 error

顺序：`meta` → `delta*` → `done`。失败时补 `error`。

**流已开始（已发 `meta`）后不能再改 HTTP 状态码**，所以网关报错时：
补发 `error` 事件、HTTP 保持 200、**不发 `done`**。

**`delta` 必须是增量**：每个 `delta.text` 是新增文本，拼接起来等于最终回答。
前端据此逐段渲染。

**Flusher 必须透传**：包装 `ResponseWriter` 的中间件若丢了 `http.Flusher`，
流式会退化成一次性返回（踩过，`stream_unsupported` 500 的根因）。

## D11 · 技能停用立即生效，智能体停用不影响已有会话

两条不同的规则，不矛盾：

| 对象 | 停用后 | 理由 |
|---|---|---|
| **技能** | 立即不进候选集 | 绑定与启用状态**每次提问重读** |
| **智能体** | 已有会话**仍可提问** | 会话锁定的是"用哪个智能体"，不是"智能体当前是否可用" |

**为什么智能体停用不影响已有会话**：教师停用智能体通常是"我不想让**新**学生用这个角色"，
不是"我要掐断正在进行的对话"。若停用即掐断，学生正在进行的提问会突然 404。

## D12 · 上下文窗口

- 最近 **6** 条消息（`historyWindow = 6`）；
- 每条正文截断 **500** 字（`histMsgMaxRunes = 500`）；
- 提问本身 ≤ **500** 字（`maxContentLen = 500`），≥2 字。

截断只影响**送进上下文的内容**，库里原文不动。

## D13 · 提问同时也是会话标题

首轮提问的前 **24** 字（`titleMaxRunes = 24`）作会话标题。
后续提问不改标题。

## D14 · 接口文档同源

`GET /openapi.json` 与 `GET /swagger/`（Swagger UI）由处理器注解生成，**同一处定义**。

**要点**：文档路由必须**注册在业务路由之前**，否则会被业务路由遮蔽
（课件 apply 页「常见故障」表明确提到这条：症状是 `/swagger` 打不开或清单里少接口）。

Swagger UI 的静态资源走 CDN（`unpkg.com`）——本机离线时页面框架能加载但样式/脚本可能失败，
这是**已知外部依赖**，不是缺陷。

## D15 · 本轮为什么不动主规约

按 AGENTS.md 硬性纪律：**`openspec/specs/` 只由 Archive 更新**。
Apply 期间回写主规约会让 delta 失去比对基线，归档时无法判断本次究竟改了什么。

所以本轮：
- 只写 `openspec/changes/add-tutor-assistant/` 下的四件套；
- 实现与 delta 逐条对齐，缺口在代码侧补；
- **归档（写回主规约）是独立的下一步**，需另行确认。

## D16 · change 命名

课程**未公布**第 5 课的 change 名。本轮自拟 `add-tutor-assistant`，
与既有 `add-class-scoped-retrieval` / `add-token-auth` / `add-token-auth` 的 `add-<能力>` 风格一致。
capability 名 `tutor-assistant` 同理。

**若日后与课程口径不一致**：改名是**目录级操作**（`git mv` 两处），
delta 内容与实现均不受影响，成本极低。
