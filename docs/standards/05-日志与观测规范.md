# 05 · 日志与观测规范

> 常驻约束。落地实现只有一个：`backend/internal/obslog`。**不要在规范之外另造日志格式。**

## 1. 一行一条 JSON

- 每条记录是**单行 JSON**，字段值里的换行由 `encoding/json` 转义成 `\n`，
  不允许出现一条日志跨多行（多行会让行式采集器把一条切成几条）。
- 固定四个键，任何日志都有：

```json
{"event":"http.access","level":"info","msg":"","request_id":"a1b2c3d4e5f60718","ts":"2026-10-27T18:20:31.472+08:00"}
```

| 键 | 类型 | 说明 |
|---|---|---|
| `ts` | string | RFC3339 带毫秒与本机时区，如 `2026-10-27T18:20:31.472+08:00` |
| `level` | string | 只有 `info` / `error` 两档 |
| `event` | string | 事件名，`<域>.<动作>`，见 §3 |
| `msg` | string | 人读说明，**可以省略**（空串时整个键不出现，不写 `"msg":""`） |
| `request_id` | string | 有则必带，无则整个键不出现（不写 `"-"`） |

- 另有按需的**小写下划线**字段：`method` / `path` / `status` / `dur_ms` / `bytes` /
  `ip` / `detail` / `server` / `tool` / `attempt` / `count`。
  调用方不得覆盖上面 5 个固定键（`obslog` 会丢弃这类覆盖，而不是让一条日志出现两个 `level`）。

## 2. 必带请求标识

- HTTP 入口的**最外层**中间件生成 `request_id`（16 位十六进制随机值），
  放进 `context.Context` 并回写到响应头 `X-Request-ID`。
  放最外层是为了让 `requireDB` 拒绝的 503、路由未命中的 404 也带同一个 id。
- 客户端可带 `X-Request-ID` 进来复用（便于端到端串链路），但必须清洗：
  长度 ≤ 64，只留 `0-9a-zA-Z-_`，否则重新生成。
  **不清洗就等于允许外部往日志里写自由文本。**
- 一次请求内产生的所有日志用同一个 id：处理器里写 `obslog.ErrorCtx(r.Context(), ...)`，
  不要用不带 context 的 `obslog.Error`。

自测：

```bash
curl -s -D- --noproxy '*' -H 'X-Request-ID: demo-001' http://127.0.0.1:18080/health | grep -i x-request-id
# 期望：X-Request-ID: demo-001
```

## 3. 字段与事件命名统一

- 事件名：`<域>.<动作>`，全小写，动作用**过去式**描述"已经发生了什么"：
  `http.access`、`server.listen`、`db.bootstrap_done`、`mcp.connect_failed`、`tool.execute_failed`。
- 域取包名的短写，不自创同义词：

| 域 | 含义 |
|---|---|
| `startup` / `server` | 进程启动、监听、关闭 |
| `db` | 连接池、建表、种子、就绪探测 |
| `http` | 访问日志 |
| `auth` | 登录、刷新、吊销、清理 |
| `index` / `qdrant` | 切片索引、向量库 |
| `search` | 检索请求与各条检索路 |
| `ask` | `/api/ask` 问答（检索前置 + 网关调用） |
| `mcp` | 服务器管理与工具清单 |
| `tool` | 会话内的工具调用 |
| `tpl` | 提示词模板 |
| `prompt` | 班级提示词 |
| `conv` | 会话编排 |
| `agent` | 智能体 CRUD 与关联 |
| `skill` | 技能 CRUD 与上传 |
| `material` | 材料列表 / 详情 / 上传 / 文件读取 |

- **不要靠 `msg` 文本做检索**。要检索的是 `event`：同一个事件在代码里只允许有一个名字，
  不同事件不允许共用名字。这是"能按事件数计数出错误率"的前提。

## 4. 敏感字段不落日志

明确禁止出现在任何日志里：

- 口令、口令哈希、access / refresh token、MCP 的 `auth_token`；
- 上传文件的正文与磁盘路径；
- 检索到的材料正文、用户提问原文（**URL query 也含提问，所以访问日志只记 `path`**）；
- 请求体整体（登录体含明文口令，上传体含材料正文）。

访问日志记录的实际字段（可核对 `cmd/server/main.go` 的 `logRequests`）：

```
method / path / status / dur_ms / bytes / ip
```

`ip` 取 `RemoteAddr`，**刻意不解析 `X-Forwarded-For`**：该头可被客户端伪造，
记它等于允许外部往审计日志里写任意地址。

迁移规则（照做即可，不需要重新设计）：

```go
// 迁移前
log.Printf("列出智能体失败: %v", err)
// 迁移后
obslog.ErrorCtx(r.Context(), "agent.list_failed", "列出智能体失败", "detail", err.Error())
```

- 处理器里有 `*http.Request` → `ErrorCtx` / `InfoCtx` 带 `r.Context()`；
  只有 `context.Context`（如索引器）→ 用同一个 ctx；
  两者都没有（进程级后台任务）才用不带 ctx 的 `Error`。
- 原 `log.Printf` 里的 `%s` 路径参数**不再落日志**（§4 禁止磁盘路径）；
  需要排障时记 `stored_name`（文件名，不含目录）与 `material_id`。

**新增代码一律用 `obslog`，不得新增 `log.Printf`。** 这条是可查的：
`grep -rn 'log\.Print' backend --include=*.go` 应无业务输出。

自测（2026-10-27 实测，23 行日志全为合法 JSON）：

```bash
grep -c '"event":"material\.' .workbuddy/tmp/server.log   # 上传/索引/忽略注入三条都在
```


## 6. 观测的最小面

除日志外，本仓只保留两处可观测信息，不引入指标/Prometheus：

- **`GET /health`**：不查库，返回 `{"status":"ok"}`，用于容器存活判定。
- **工具调用审计表 `mcp_tool_calls`**：每次外部工具调用落一行（含失败的），
  字段 `server_name / tool_name / arguments / result / status / error_text / duration_ms`。
  它是**业务可观测性**的主要来源——"这个工具到底被调了几次、成功率多少、慢在哪"都从这张表查，
  比翻日志可靠（日志会被轮转，审计表不会）。
